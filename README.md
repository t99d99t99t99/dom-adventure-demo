## 작품 소개
**DOM Adventure**: Snake 게임을 하다가 화면에 문제가 생기고, 개발자 도구를 이용해 직접 페이지를 복구해야 하는 짧은 웹게임입니다..

### 플레이 방법

1. `index.html`을 데스크톱 Chrome에서 엽니다.
2. 이후에는 화면에 나타나는 지시와 단서에 따라 게임을 플레이합니다. 어떻게 해야 다음 단계로 나아갈 수 있을지 알아내는 것은 플레이어의 몫입니다.

데스크톱 Chrome 사용을 권장하며, 모바일 환경에서는 원활한 플레이가 어렵습니다.

### 구현 구성

- `index.html`, `css/style.css`: 시작 화면과 공통 화면 스타일
- `snake.html`, `js/snake.js`, `css/snake.css`: Snake 게임, 조작, 효과음, 오류 전환
- `report.html`, `js/report.js`, `css/report.css`: 오류 안내, 단계별 튜토리얼, 과일 예제, 배경 복구 연출
- `demo-ending.html`: 숨겨진 엔딩과 다시 시작하기 버튼
- `assets/audio/`: Snake 효과음

라이브러리나 빌드 도구 없이 HTML, CSS, JavaScript로 구성했습니다. 플레이어가 개발자 도구에서 프로젝트의 실제 코드를 살펴볼 수 있도록 기능별 파일을 나누고, 읽기 쉬운 이름과 설명을 사용하는 것을 목표로 했습니다.

## 질문

> 개발자 도구를 사용자 경험의 일부로 끌어온다면 어떻게 될까?

## 질문과 조사

웹 브라우저의 개발자 도구는 보통 페이지를 만드는 사람이 오류를 찾고 코드를 살펴볼 때 사용합니다. 개발자가 아닌 일반적인 사용자라도 언제든 접근할 수 있지만 보통은 그다지 관심을 가지지도 않고, 막상 열어도 복잡하게 생겨서 어떻게 사용할 수 있는지 알기 어려운 경우가 많습니다. 이 게임은 그런 개발자 도구를 게임을 계속하기 위해 직접 사용해야 하는 장소로 바꾸어 보는 실험입니다.

### 참고한 작품

- [CSS Diner](https://cssdiner.com/)는 CSS 선택자를, [Flexbox Froggy](https://froggy.dotus.store/)는 Flexbox를, [CSS Grid Garden](https://cssgridgarden.com/)은 CSS Grid를 게임으로 익히게 합니다. 세 게임 모두 플레이어가 CSS 코드를 쓰고, 그 코드가 게임 화면의 대상들을 어떻게 선택하거나 옮기는지 바로 확인하는 방식이 재미있고 효과적인 튜토리얼이라고 느꼈습니다.

제가 이 작품들에서 더 이어 가고 싶은 지점은 코드가 바꾸는 범위입니다. 이 게임들에서는 코드가 게임 영역 안의 사물을 움직이거나 선택합니다. 반면 DOM Adventure에서는 개발자 도구에 입력한 명령이 게임 바깥의 실제 웹 문서에 작용합니다. 플레이어가 페이지의 보호막을 직접 제거해 다음 화면을 드러내면서, 코드가 웹페이지 자체를 바꾸는 경험으로 이어지도록 했습니다.

이번 MVP에서는 작동하는 흐름을 만드는 데 집중했습니다. 플레이어는 Snake를 조작하다가 오류 화면을 만나고, F12로 개발자 도구를 연 뒤 콘솔의 안내를 따라 `report.html`로 이동합니다. 안내를 읽고 예제에서 `document.getElementById()`와 `remove()`를 연습한 다음, 실제 페이지의 `barrier`를 제거하면 가려져 있던 다음 화면이 드러납니다.

이 흐름으로 확인하고 싶은 점은 다음과 같습니다.

- 개발자 도구를 게임 안의 장소처럼 제시하면 사용자가 호기심을 느낄 수 있을까?
- 직접 페이지를 바꾸는 행동이 설명을 읽는 것보다 DOM의 역할을 이해하는 데 도움이 될까?
- 처음 보는 도구의 부담을 단계별 안내와 작은 연습 예제로 줄일 수 있을까?

## AI 활용 과정

AI를 코드 작성과 반복적인 프로토타이핑에 사용했습니다. Snake 화면과 입력 처리, 오류 전환, 콘솔 메시지, 단계별 튜토리얼, 예제 화면, 배경이 사라지는 연출의 초안을 함께 구현했습니다.

작업은 한 번의 생성으로 끝나지 않았습니다. 저는 기능의 목적과 플레이 경험을 정하고, 실행해 본 뒤 구체적인 수정 요청을 이어 갔습니다. 예를 들어 튜토리얼을 한꺼번에 보여 주지 않고 한 단계씩 넘기도록 바꾸고, 낯선 개발 용어를 쉬운 설명과 과일 예제로 풀도록 조정했습니다.

AI가 제안한 코드는 그대로 완성품으로 간주하지 않고 프로젝트의 실제 흐름과 맞는지 확인하며 수정했습니다. 특히 이 작업은 플레이어가 소스 코드를 직접 탐색하므로, 동작뿐 아니라 코드가 읽히는지도 중요한 설계 기준으로 삼았습니다.

## 실패와 배운 점

- 처음에는 배경을 한 번에 제거했습니다. 플레이어가 페이지를 직접 고쳤다는 감각이 약하고, 제거 순간을 연출에 연결하기도 어려웠습니다. 배경 제거 여부를 감지한 뒤 캔버스에서 위쪽부터 먼지처럼 흩어지도록 바꾸었습니다.
- 배경 제거 시 먼지 입자를 각각 DOM 요소로 만들었더니 화면이 버벅였습니다. 시각 효과 하나도 구현 방식에 따라 성능이 크게 달라질 수 있음을 배웠습니다. 입자를 개별 요소로 늘리는 대신 캔버스에 그리도록 바꿨습니다.
- 튜토리얼 내용을 한 화면에 모두 보여 주면 부담스러웠습니다. 설명을 단계별로 나누고, 먼저 작은 예제에서 명령을 연습한 뒤 실제 페이지에 적용하도록 순서를 정리했습니다.
- 처음부터 개발자 용어를 많이 쓰면 안내가 장벽이 됩니다. HTML, 요소, 콘솔 같은 말을 일상적인 비유와 구체적인 행동에 연결해 설명하는 편이 이 프로젝트의 목적에 맞았습니다.
- 처음에는 콘솔에 `report.html` 링크를 출력해 플레이어가 클릭하도록 하려 했습니다. 하지만 링크를 누르면 새 탭이 열려 Snake 화면이 원래 탭에 남았고, 그 탭에서 노이즈도 계속 재생됐습니다. 링크 하나가 페이지 이동 방식과 사운드까지 바꿔 놓은 셈입니다. 그래서 URL을 클릭하게 하는 대신 `reportCorruption()`을 콘솔에 입력하도록 바꾸었습니다. 이 함수는 현재 탭에서 보고서로 이동하므로 게임 화면을 떠나면서 소리도 함께 멈춥니다.
